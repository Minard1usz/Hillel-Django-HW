# Hillel-Python-HW
## 🏗️ Архітектурні особливості та технологічні рішення

У рамках проєкту було проведено масштабний рефакторинг та впроваджено сучасний стек технологій для забезпечення максимальної швидкодії, безпеки та стійкості вебдодатка до високих навантажень.

### 1. Асинхронна архітектура (Asynchronous Views)

Для оптимізації I/O-bound операцій ключові компоненти системи переведені на асинхронний режим:

* **Паралельне виконання запитів (`asyncio.gather`):** На головній сторінці магазину (`store`) реалізовано одночасне паралельне виконання 5 незалежних SQL-запитів до бази даних (фільтрація, агрегація та підрахунок книг у категоріях). Це знизило загальний час відгуку сторінки до мінімально можливого (замість послідовного очікування кожного запиту).
* **Гібридний контекст:** Використання інструменту `sync_to_async` дозволило безпечно інтегрувати синхронну ORM Django, механізм сесій та роботу з авторизованими користувачами (`request.user`) в асинхронний event loop без блокування потоків.
* **Асинхронний Class-Based View (`BookListView`):** Реалізовано асинхронний метод `get` з неблокувальним приведенням QuerySet до списку в пам'яті розробника.

### 2. Захист від Race Conditions та Оптимізація БД

* **Блокування рядків на рівні БД (`select_for_update`):** Процес оформлення замовлення повністю захищений від "стану гонитви" (Race Conditions), коли кілька користувачів одночасно намагаються придбати останню книгу на складі. Метод `select_for_update()` блокує рядок товару в базі даних всередині ізольованої транзакції до моменту успішного списання кількості.
* **Атомарні транзакції (`transaction.atomic`):** Створення замовлення (`Order`), формування позицій чека (`OrderItem`) та списання залишків зі складу виконуються як єдина неподільна операція. У разі виникнення помилки (наприклад, `InsufficientStockError`), база даних миттєво відкочується до початкового стану.
* **Вирішення проблеми N+1:** Усі списки книг оптимізовані за допомогою `select_related('category')`, що дозволяє завантажувати пов'язані дані за один SQL `JOIN` запит замість сотень окремих звернень до БД.

### 3. Багаторівневе кешування (Redis/Memcached)

* Для зниження навантаження на PostgreSQL впроваджено паттерн **"Кеш на читання"** за допомогою методу `cache.get_or_set`.
* Список категорій, який рідко змінюється, але запитується на кожній сторінці каталогу, зберігається в кеші із заданим таймаутом (TTL). Це дозволяє віддавати дані миттєво без повторного сканування таблиць БД.

### 4. Інтеграція з платіжною системою Stripe API

* **Фінансова точність:** Реалізовано безпечну конвертацію грошових сум із типу `Decimal` у мінімальні одиниці валюти (копійки для Stripe) за допомогою суворого банківського округлення `ROUND_HALF_UP` через метод `.quantize()`.
* **Захист від подвійних списань:** Для запитів до Stripe інтегровано генерацію унікальних ключів ідемпотентності (`idempotency_key`), що унеможливлює повторне зняття коштів при випадковому подвійному кліку користувачем на кнопку оплати.

### 5. Повне покриття тестами (Pytest) та Документація (PEP 257)

* **29 успішних тестів:** Проєкт покритий надійною базою юніт- та інтеграційних тестів за допомогою `pytest-django`. Тести перевіряють як роботу асинхронних view-компонентів, так і сувору валідацію моделей (наприклад, обмеження на обов'язкові поля, перевірку поведінки числових полів на рівні транзакцій `transaction=True`).
* **Стандартизована документація:** Усі класи, в'юхи та допоміжні утиліти мають розширені `docstrings` за стандартом **PEP 257** із детальним описом вхідних аргументів (`Args`) та результатів роботи (`Returns`), що робить код легким для підтримки (Maintainability).
